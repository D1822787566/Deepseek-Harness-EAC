# 离线启动性能第一阶段设计

## 目标

在离线模式下，桌面端自动启动不发起 dsh、客户端或内置插件的更新检查；同时把关键启动阶段的实际耗时写入现有启动日志，供后续定位安装版与便携版共同的本地 I/O 瓶颈。

## 范围

本阶段只修改 `dsh-desktop/main.js` 及其测试：

- 离线模式时不创建三类自动更新定时器。
- 三个自动更新执行入口也在非手动调用时拒绝执行，避免后续调用点绕过调度保护。
- 手动“检查更新”保持可用。
- 为启动关键路径记录阶段及总耗时；日志不包含用户路径、密钥或网络响应。

不在本阶段修改完整性校验、插件同步顺序、窗口创建时机或 portable 解压缓存。这些变更会影响故障检测与启动恢复语义，应在有阶段耗时数据后单独设计。

## 方案选择

推荐“调度层 + 执行层双重保护”。仅在调度层判断离线模式能减少进程创建，但无法阻止别的自动调用点；仅在执行层判断会留下无意义定时器。两者一起使用，且以 `manual === true` 明确保留用户主动检查。

启动计时采用主进程内单次 `process.hrtime.bigint()` 基准。每个阶段通过一个小型本地 helper 落一条现有 `boot` 日志，完成时再落总耗时，避免引入新依赖或持久化状态。

## 数据流

`boot()` 建立计时基准后：

1. 在同步插件、异步预检、完整性校验、`dsh web` 就绪后分别记录耗时。
2. 在服务成功就绪后的自动任务注册位置读取 `offlineMode`。
3. 离线时只记录“已跳过自动更新检查”；联网时保留现有注册逻辑。
4. `runUpdateFlow(false)`、`runClientUpdateFlow(false)`、`runPluginUpdateCheck(false)` 各自再次检查离线模式后返回；传入 `true` 时不检查，保留手动菜单行为。

## 错误处理与兼容性

- 日志写入失败沿用 `log()` 的既有容错，不影响启动。
- `offlineMode()` 读取失败时现有实现默认为离线，因此自动检查仍安全地跳过。
- 不更改环境变量 `DSH_DESKTOP_SKIP_*` 和 `DSH_DESKTOP_OFFLINE=0` 的既有优先级。
- 所有自动检查的已有时间间隔、联网模式行为与手动更新 UI 保持不变。

## 验收与测试

- 静态/单元测试证明：三处自动调度均受离线判断包围。
- 静态/单元测试证明：三个自动入口在 `manual === false` 时包含离线短路，手动调用未被短路。
- 静态/单元测试证明：`boot()` 记录关键阶段与总耗时。
- 相关 Node 测试、语法检查和全量测试通过。
